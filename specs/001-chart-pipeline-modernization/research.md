# Research: Chart Generator Pipeline Modernization

**Feature**: 001-chart-pipeline-modernization
**Purpose**: Before specifying or planning changes, verify the incoming audit's claims directly against the actual source (`chart.py`, `generator.py`, `effects.py`, `themes.py`) so the spec is built on confirmed facts, not restated assertions. Every row below is either **Confirmed** against a cited file:line range, **Corrected** (audit was imprecise or understated), **New** (found during this review, not in the audit), or **Unverifiable** (needs an artifact we don't have, e.g. `custom_config.py`, or a profiling run).

Files reviewed: `chart.py` (4,812 lines), `generator.py` (4,131 lines), `effects.py` (491 lines), `themes.py` (1,105 lines). Method: static reading (`grep`/`view`) — no execution, no profiler was run against this codebase in this review, so any latency multiplier is an estimate to validate, not a measurement.

## 1. Performance-path findings

| # | Claim | Status | Evidence |
|---|---|---|---|
| 1.1 | `get_window_extent(renderer)` is called per-artist and is the dominant per-image cost | **Confirmed** | 66 call sites in `generator.py` (`get_granular_annotations`, `get_detailed_annotations`, `add_graph_topology_metadata`, `get_subchart_detection_annotations`, `create_unified_annotation`, `apply_realism_effects` indirectly via label bboxes). Each forces a synchronous Agg rasterization of that artist's path. |
| 1.2 | `has_non_background_pixels` scans `fig.canvas.buffer_rgba()` per label | **Confirmed, and worse than described** | `generator.py:195-266`. It calls `fig.canvas.draw()` and `buffer_rgba()` (full-figure RGBA buffer) per label, then samples pixels in a stride loop. But the loop's own detected result is **never returned** — the function falls through to an unconditional `return True` after the loop (`generator.py:256-257`), and the code below it (`generator.py:259-264`) is dead: an unreachable `return False` / `except Exception as e: return True` after the first `try` block already returned. In its current form the function costs a full canvas redraw + RGBA buffer read per label and then almost always returns `True` regardless of what it found — it is not merely slow, it currently does close to nothing useful. This *raises* the value of simply removing it rather than optimizing it. |
| 1.3 | `get_granular_annotations` is a single very large function mixing dispatch, geometry extraction and validation | **New** (not in audit) | `generator.py:268-1277` — ~1,009 lines in one function. `get_detailed_annotations` (`1906-2169`, ~263 lines) and `create_unified_annotation` (`2391-2835`, ~444 lines) are similarly large. This is a testability/maintainability risk independent of raw speed: none of the P0 geometry fixes below can be unit-tested in isolation while they live inside these functions. |
| 1.4 | Parallelism via `ProcessPoolExecutor` | **Confirmed** | `generator.py:4045-4046`. The claim that per-process `buffer_rgba()` reads and FreeType glyph rasterization can contend for CPU/memory across workers is architecturally plausible given 1.1–1.2, but was not independently benchmarked in this review. |

## 2. Geometry-fidelity findings

| # | Claim | Status | Evidence |
|---|---|---|---|
| 2.1 | Perspective/homography transforms are propagated to annotations by re-deriving an axis-aligned box from the min/max of the 4 warped corners ("AABB dilation") | **Confirmed** | `generator.py:1598-1610`, inside `apply_realism_effects`. The 4 corners of `ann['bbox']` are individually warped (`_warp_point`/`_rotate_point`, `generator.py:1522-1562`, which correctly implement the homogeneous-coordinate homography and are reused per-vertex for keypoints), but the result is immediately collapsed back to `transforms.Bbox.from_extents(min(xs), min(ys), max(xs), max(ys))` (`generator.py:1609`). The exact 4 warped points are computed and then thrown away. |
| 2.2 | Two perspective effects exist with inconsistent annotation safety | **New** (not in audit — more severe than 2.1) | `generator.py:1511-1512` registers both `"perspective": apply_perspective_effect` and `"perspective_warp": apply_perspective_warp_effect` in `effect_function_map`. The dispatch loop (`generator.py:1564-1591`) only special-cases `"perspective_warp"` (line 1584) to capture the homography `H` and append a `("homography", H)` transform step. When `"perspective"` fires instead, it falls into the generic branch (`generator.py:1588-1589`, `pil_img = func(pil_img, **params)`) and `apply_perspective_effect` (`effects.py:269-298`) does not return a homography at all — no transform step is appended. Net effect: if this branch fires, the image is warped by an SVD-derived homography but **every annotation for that image is left completely untransformed** — not dilated, simply wrong. This is a correctness bug the audit did not describe. Whether it fires in production depends on the probability `p` configured for the `"perspective"` key, which lives in `custom_config.py` (`OCR_TRAINING_CONFIG`, imported at `generator.py:75-85`) — **not included in the uploaded files**, so severity/frequency is unverified pending inspection of that config. |
| 2.3 | `stroke_to_polygon_ribbon` has no self-intersection handling and no clip-based boundary handling | **Confirmed** | `generator.py:1703-1731`. Per-vertex normal is the average of adjacent segment normals (`1721-1722`); at sharp curvature this can flip sign or self-cross with no correction. Truncation of off-canvas points is not addressed in this function (clamping, if any, happens at the call site). |
| 2.4 | Amodal/modal decomposition is entirely absent | **Corrected** | It is **already implemented for area charts**. `extract_area_segmentation_annotations` (`generator.py:1791-1833`) has an explicit design note in its own docstring: the polygon is built from `fill_top`/`fill_bottom` which `chart.py`'s `_generate_area_chart` already encodes per-mode — full amodal region (`bottom=0`) for `overlapping`/`single` modes, or a mutually exclusive band (`bottom=y_stack_previous`) for `stacked` mode. The gap is real but narrower than stated: it applies to **bars occluded by error bars/labels** and to **line-series crossings** (2.3), not to area charts. |
| 2.5 | `ensure_min_bbox_thickness` symmetric padding | **Confirmed as described** | `generator.py:147-188`. Independently pads X and Y deficits to a 4px minimum. This is a deliberate trade-off (prevents zero-area boxes) with the side effect the audit names (can create synthetic overlap with a neighboring box); not a bug, but worth revisiting once OBB support exists, since OBB removes the reason 1D elements degenerate to zero area under rotation. |

## 3. Semantic/relational findings

| # | Claim | Status | Evidence |
|---|---|---|---|
| 3.1 | Series identity for grouped/stacked bars is unreliable due to centroid-distance matching | **Corrected — more fundamental than described** | `extract_bar_info` in `chart.py:4637-4671` hardcodes `"series_idx": 0` for **every** bar (`chart.py:~4658`), with an explicit comment `# Would need to determine series in multi-series charts`. This isn't an occasional mismatch from a distance heuristic — there is currently **no series discrimination at all** in bar ground truth. Multi-series bar charts (grouped or stacked) cannot currently supervise series-aware GNN training on bars. |
| 3.2 | Baseline/axis linkage for twinx (dual-axis) charts uses a fragile nearest-distance heuristic | **Confirmed, but is a separate mechanism from 3.1** | `add_graph_topology_metadata`, `generator.py:2169-2328`. Bars are matched to the nearest `baseline` by absolute pixel distance from bar-bottom to candidate baseline y, filtered by x-range containment (`generator.py:2287-2300`). This assigns which **axis** a bar belongs to (primary vs. secondary/twinx) — not which **series**. Both problems are real and both need fixing, but they are not the same bug and the spec treats them as two separate requirements. |
| 3.3 | `themes.py` vocabulary is disconnected from chart data domain, producing semantically mismatched axis pairs | **Confirmed structurally** | `themes.py` is 1,105 lines of static Python lists/tuples (`SCIENTIFIC_Y_LABELS`, `COMPARATIVE_LABELS`, etc.) with zero functions and no cross-list domain tagging beyond the list name itself. The actual sampling call sites that pair an x-label list with a y-label list live in `chart.py`/`generator.py` and would need to be located and constrained to a shared domain key as part of implementation — flagged as a task, not fully enumerated in this review. |

## 4. Confirmed supporting context (not defects, background for the plan)

- `chart.py` does implement the statistically sophisticated generators the audit credits it with: Hill-equation dose-response (`chart.py:101-119`), Michaelis-Menten kinetics (`chart.py:178-185`), AR(1) noise (`_ar1_noise`, `chart.py:2455`), ALR/simplex transforms for compositional (pie) data (`alr_transform`/`inverse_alr_transform`, `chart.py:702-717`), optimal-leaf-ordering and spectral/Fiedler-vector matrix seriation (`MatrixSeriator`, `chart.py:3877-3915`), Perlin/fractal spatial noise (`SpatialCoherenceGenerator`, `chart.py:3642-3701`), MCAR/MNAR missingness injectors (`MissingDataInjector`, `chart.py:3732-3815`), and multiple heteroscedastic-noise and covariance-construction utilities. This is real, non-trivial modeling work that the modernization plan should preserve untouched — the problems are in the annotation/rendering layer (`generator.py`, `effects.py`), not in `chart.py`'s statistics.
- `generator.py` is single-backend: `matplotlib.use('Agg')` (`generator.py:4`), with a hard runtime dependency on an external `custom_config.py` (`OCR_TRAINING_CONFIG`) that defines class maps and (presumably) effect probabilities. That file was not provided and must be read before P0 execution begins (see Open Questions).

## 6. Open questions this review could not resolve

These require either a file we don't have or a decision only the project owner can make; they are carried into `spec.md` as `[NEEDS CLARIFICATION]` markers.

1. **`custom_config.py` contents** — the actual probability, if any, assigned to the `"perspective"` effect key (§2.2), and the exact schema of `OCR_TRAINING_CONFIG`'s class maps, are unknown. P0 work cannot be scoped precisely until this file is read.
2. **Backward compatibility requirement** — does anything downstream currently consume the emitted AABB `.txt`/JSON schema in production (e.g., an already-trained detector, a labeling QA tool)? This determines whether OBB output must be additive-with-a-flag or can replace AABB outright.
3. **Performance baseline** — no profiling run exists yet for this codebase in this review. The "3–5×" and "15–25% mAP" figures in the source audit are targets to validate empirically (Task T0 in `tasks.md` establishes the baseline), not verified measurements.
4. **Vector backend scope** — should the SVG/Vega-Lite path fully replace Matplotlib for all 8 chart types in one pass, or ship chart-type-by-chart-type behind a feature flag with Matplotlib as the default until each type reaches parity? The plan assumes the latter (lower risk); confirm before P1 starts.

## 7. Second-pass findings (independent review, verified against source, 2026-09-17)

An external reviewer proposed six additional defects after reading this document. None of the six arrived with file:line citations, so each was re-verified directly against `chart.py`/`generator.py`/`effects.py` before being trusted — the same standard §1-§3 above applied to the original audit. All six are **Confirmed**; two required a correction to the *mechanism* the reviewer described. All six are P0-severity (pure correctness bugs, no new dependency) and are folded into `spec.md`/`plan.md`/`tasks.md` as FR-019–FR-024.

| # | Claim | Status | Evidence |
|---|---|---|---|
| 7.1 | Segmentation masks, pose keypoints, marker boxes, and the re-derived per-chart-type object boxes bypass `apply_realism_effects` entirely | **Confirmed** | `apply_realism_effects` runs at `generator.py:3400`. `extract_area_segmentation_annotations` (called 3500), `extract_pie_pose_annotations` (3528), and `extract_line_segmentation_annotations` (3557) all run *after* that point but read coordinates directly via `ax.transData.transform_point` (1364-1368, 1765, 1782, 1824) — never touching `transform_steps`, which is local to `apply_realism_effects` and not exposed anywhere. Worse, `get_granular_annotations` (which itself only ever reads from the raw `fig`, 268-281) is called a *second* time for the `area_obj`/`pie_obj`/`line_obj` streams (3493, 3518, 3550), after effects have already been baked into `pil_img` — so those boxes are regenerated from the untouched figure and are not merely desynchronized, they are simply pre-effect coordinates mislabeled as post-effect ones. This is a materially larger version of the §2.1 AABB-dilation finding: four of seven label streams, not one, silently ignore every geometric realism effect. |
| 7.2 | `extract_bar_info`'s `series_idx: 0` bug (§3.1) has a deeper root cause than "the function needs fixing" | **Confirmed — corrects and deepens §3.1** | `_generate_bar_chart` already computes correct per-bar `series_idx`/`bar_idx`/`bottom`/`top`/`center` for both `side_by_side` and `stacked` styles (chart.py:1511-1620). `generator.py` captures this as `bar_info_list` from the generator function's return value (3154/3182/3184) — but the `chart_info_map[ax] = {...}` dict literal that follows (~3222-3238) never stores it. `create_unified_annotation` (2391) then re-derives bar info from scratch via `extract_bar_info(ax, chart_type)` at line 2585 — the same hardcoded-`0` scraper §3.1 already flagged. The correct fix is not "make `extract_bar_info` smarter" (as this review's own `plan.md`/`tasks.md` drafts originally proposed); it is "stop calling it and read the data that already exists." |
| 7.3 | A canvas-resize effect (e.g. `pdf_document_context`) occurring after a rotation/homography effect corrupts the geometric transform applied to annotations | **Confirmed, mechanism corrected** | `apply_realism_effects` sets `img_w, img_h = pil_img.size` once at line 1520, then reassigns both at line 1595 to the **final**, post-all-effects size. `_apply_transform_steps` and its callers (`_rotate_point`, `_warp_point`) only execute afterward, in the per-annotation loop starting at 1598 — so the `img_h - y` origin-flip inside them always uses the final canvas size, even though `apply_perspective_warp_effect` (effects.py:324) computes `H` from `w, h = pil_img.size` *at the moment it fires* (dimension-dependent: `dx = w * distortion_factor`, etc.), and `apply_pdf_document_context_effect` (effects.py:412) can grow the canvas afterward via padding (`new_h = h + total_top_padding + ...`). This is real, but the reviewer's stated cause — "translation applied before homography in `if/elif` order" — is not: `_apply_transform_steps` dispatches correctly regardless of branch order. The actual mechanism is a Python closure gotcha: `img_w`/`img_h` are captured by reference from the enclosing scope, not by value, and get silently rebound to the final size before any point is actually warped. |
| 7.4 | Out-of-bounds annotations are discarded rather than clipped, for every chart type except heatmaps | **Confirmed, exact match** | `generator.py:3452-3458`: any annotation whose box extends past `[0,W]×[0,H]` by even a fraction of a pixel after effects is dropped with a `print(f"    - Discarded annotation (out of bounds after effects): ...")`. Heatmaps alone get a proper `min`/`max` clamp (3442-3451). This systematically strips tick labels, axis titles, and margin-adjacent bars under routine `scan_rotation`/padding effects. |
| 7.5 | `batch_merge_all` is referenced but never defined or imported | **Confirmed** | Only appears at `generator.py:4110` and `4112`; absent from the file's import block and from `chart.py`/`effects.py`/`themes.py`. Fires a `NameError` only when `dataset_format != 'multi_chart_detection'` and `merge_json_files: True` — an easy-to-miss config combination, consistent with this surviving undetected. |
| 7.6 | `apply_chart_theme`'s global `rcParams` mutation leaks font state | **Confirmed, and more acute than described** | `apply_chart_theme` sets `rcParams['font.sans-serif']` globally (chart.py:374). The reviewer frames this as leakage *between separate images* in a `ProcessPoolExecutor` worker (research.md §1.4 confirms that pool exists) — true, but secondary. The sharper bug: `theme_name` is chosen **per-axis**, inside the per-subplot loop (`generator.py:3104`, `random.choice` at 3129), and Matplotlib resolves the default sans-serif family at draw time, not at text-creation time. A `multi_chart_detection` composite figure (1-4 subplots per `min_subplots`/`max_subplots`, 1422-1423) with a different theme per subplot will therefore render **every subplot's text in whichever theme's font was set last** — a bug within a single image, not only across a worker's lifetime. |

All six require no artifact this review lacks (unlike the three items in §6) and no profiling run — they were confirmed the same way as §1-§3, by direct static reading. They are scoped into P0 (`spec.md` FR-019–FR-024, `plan.md`'s Phase P0 roadmap items 9-13, `tasks.md` Phase 6) rather than treated as a new open question.

## 8. Third-pass findings (independent review, verified against source, 2026-09-18)

A third, again unattributed, set of seven claims was checked the same way as §6-§7. Three are **Confirmed — new**. One is **Confirmed but already mitigated** by the §7 fix already scoped into P0. Three are **Not confirmed** — either refuted outright by the source or describing a risk that doesn't actually manifest in this codebase. None of the three new findings requires a new dependency; they are scoped into P0 as FR-025–FR-027, continuing the FR sequence rather than reusing FR-019/FR-020 (already assigned in §7's addendum).

| # | Claim | Status | Evidence |
|---|---|---|---|
| 8.1 | Matplotlib/Pillow coordinate-system mismatch (bottom-left vs top-left origin) causes silent vertical drift when a homography is applied | **Not confirmed — restates §7.3 under a different frame** | `_rotate_point`/`_warp_point` (generator.py:1522-1550) correctly flip matplotlib (bottom-left) coordinates to image (top-left) space before warping and flip back after, and `apply_perspective_warp_effect`'s `src_pts`/`dst_pts` (effects.py:329-330) are genuinely defined in top-left/y-down convention, matching what `_warp_point` assumes — so there is no coordinate-*convention* bug. The only way drift occurs is if the canvas size used for the flip differs between when `H` was computed and when it's applied — which is exactly the closure-variable bug already confirmed in §7.3 and scoped as FR-021. No new defect; no new action. |
| 8.2 | Missing `plt.close(fig)` causes a Matplotlib memory leak across `ProcessPoolExecutor` workers | **Refuted** | `generate_single_chart_task` (generator.py:3959-3978) — the exact callable passed to `executor.map` — already wraps its work in `try/except/finally`, with `finally: plt.close('all')` executed unconditionally on every task regardless of success or exception. The specific gap alleged does not exist in this file. |
| 8.3 | Rotated tick-label text yields an inflated axis-aligned `get_window_extent()` box, independent of any `effects.py` transform | **Confirmed — new** | `chart.py` rotates x-tick labels at 45°/90° in several places (432-434, 1392, 3286). None of the ~30 `label.get_window_extent(renderer)` call sites across `generator.py` (407-945 and beyond) compensate for this — `get_rotation()` does not appear anywhere in `generator.py` or `chart.py`. Distinct from §2.1 (which concerns *effects.py's* post-render dilation, not Matplotlib's own rendering of rotated text). Scoped as FR-025. |
| 8.4 | DPI/canvas-resolution drift between figure creation, `savefig`, and Pillow resizes | **Not confirmed — doesn't manifest in this codebase** | `fig.savefig(buf, dpi=output_dpi)` (3258) uses the same `output_dpi` the figure was created with. Every `.resize()` in `effects.py` (105, 111-112, 245-246) round-trips back to its original dimensions. `img_w`/`img_h` is already read from the actual rendered buffer (`Image.open(buf).size`, ~3286) rather than computed from `figsize × dpi`. No drift path exists to fix. |
| 8.5 | Homography-warped OBB corners can form a self-intersecting ("bow-tie") or inconsistently-wound quadrilateral near the vanishing line | **Confirmed — new, and flags a dependency conflict in the claim's own fix** | Mathematically real: a projective transform only preserves convexity/winding while all 4 points stay on one side of the vanishing line ($H_{20}x + H_{21}y + H_{22} = 0$); nothing in the current plan validates this once FR-001/FR-002 start exporting individually-warped corners. Frequency depends on `distortion_factor` (unverified — same `custom_config.py` gap as §6.1). The claim's suggested fix (`shapely.geometry.Polygon(...).convex_hull`) cannot be used where this matters: FR-001/FR-002 are P0, and P0 forbids new dependencies while `shapely` is P1-only in this plan. A 4-point convex-hull/winding check is trivial in pure NumPy (sign of consecutive edge cross-products), so FR-026's fix is scoped dependency-free. |
| 8.6 | NumPy scalars (in particular unconverted ones) crash `json.dump` | **Partially confirmed, mostly refuted** | `detailed_json` already passes through a recursive `convert_numpy_types` (generator.py:1883-1901) handling `np.integer`, `np.floating`, `np.ndarray`, and matplotlib `Bbox` — the blanket "any NumPy scalar crashes it" framing is wrong for this path. Two real, narrower gaps remain: (a) `np.bool_` is not a subclass of Python `bool` in NumPy, so it isn't caught by any `isinstance` branch and falls into the catch-all, silently becoming the *string* `"True"`/`"False"` rather than a JSON boolean — a correctness bug, not a crash; (b) `ocr_json` and `metadata_json` (3947-3953) bypass `convert_numpy_types` entirely — harmless today only because both are numpy-free by construction, but a latent crash for the OCR-integration work the code's own comments mark as pending (`"This would normally come from OCR processing"`). Scoped as FR-027. |
| 8.7 | Clamping out-of-bounds boxes (the §7.4/FR-022 fix) can produce degenerate micro-slivers that destabilize IoU-based losses | **Confirmed as a real concern — already mitigated, no new action** | Legitimate failure mode in general. But FR-022/T028 (§7, previous pass) already gates the clamped box on the existing `MIN_BBOX_SIZE = 8` local constant (generator.py:3406, already used identically for the pre-effects size filter) before keeping it — a box that clamps down below that threshold is dropped, not exported as a sliver. No spec/task change required; recorded here so it isn't re-litigated. |

FR-025–FR-027 (rotated-text OBB fidelity, OBB convexity/winding guarantee, uniform NumPy/boolean JSON safety) are folded into `spec.md` as a second P0 addendum, `plan.md`'s P0 roadmap items 14-16, and `tasks.md`'s new Phase 7. §8.1, §8.2, §8.4, and §8.7 require no changes to `spec.md`/`plan.md`/`tasks.md` — they are recorded here as the audit trail for why they were considered and set aside.

## 9. Fourth-pass findings (independent review, verified against source, 2026-09-18)

A fourth, unattributed set of seven claims was checked the same way as §6-§8 — this time including one claim about the spec kit's *own* testing methodology (§9.7), not just the four source files. Four are **Confirmed — new** (one of them narrower than claimed). Two are **Refuted** outright — both already mitigated in existing code, one of them with a comment documenting the fix. One is a **valid general risk with no current manifestation**, recorded as forward guidance rather than a fix. None of the four confirmed findings requires a new dependency.

| # | Claim | Status | Evidence |
|---|---|---|---|
| 9.1 | `twinx()` secondary-axis z-order collision produces incorrect layering between primary/secondary axes | **Confirmed as a valid general risk — no current manifestation** | `twinx()` is used exactly once (chart.py:1319, the dual-Y-axis bar chart), and Matplotlib's "second axes draws on top by default" behavior is real and well-documented. But this specific generator places the two bar groups at deliberately non-overlapping x-position ranges (`positions_2 = np.arange(num_bars_2) + num_bars_1 + gap`, chart.py:1332), so no actual visual occlusion occurs. `generator.py` also never calls `get_zorder()` anywhere — there is no existing z-order-based occlusion logic to be wrong. No fix scoped; recorded as a constraint any *future* overlapping-twinx chart type (e.g. a bar+line combo) must satisfy. |
| 9.2 | PRNG state is duplicated across forked `ProcessPoolExecutor` workers, causing duplicate synthetic charts | **Refuted** | `generate_single_chart_task` (generator.py:3963-3964) already re-seeds both `random` and `np.random` from `base_seed + i` (the task's own unique index) at the start of every task — the line directly above it is commented `# Re-seed to prevent process replication duplication`. `torch` is not used anywhere in this codebase. |
| 9.3 | Matplotlib's RGBA canvas buffer crashes or corrupts on JPEG export | **Refuted** | The working image is forced to RGB immediately after rendering (`Image.open(buf).convert('RGB')`, generator.py:3389), and the only save calls write `.png` (3476, 3782) — never `.jpg`/`.jpeg`. The sole `.jpg` reference in the codebase (effects.py:21) is an in-memory JPEG-compression-artifact simulation operating on an already-RGB array; it never touches disk as a final image. |
| 9.4 | Non-positive values crash or silently mask points on log-scaled axes | **Confirmed — narrower than claimed** | `apply_axis_scaling` (chart.py:442-471) already guards exactly this case — `if data_min is None or data_min <= 0: scale_type = 'symlog'`, with a comment flagging it `CRÍTICO` and a defensive `try/except` around the actual `set_yscale`/`set_xscale` calls. Two of its three call sites compute `data_min` correctly from the real, final plotted data (line chart, 1826; scatter, 2066). The third — the area chart (chart.py:3044) — passes a **hardcoded** `data_min=0.01`, bypassing the check entirely regardless of what `boundary_y`/`y_stack` actually contain. ### 10.4 Confirmed gaps and discrepancies

1. **FR-023 Default Fallback Config Incomplete**:
   - `generator.py:89` still raises `ImportError("custom_config.py could not be found.")` if `custom_config.py` is absent. 
   - *Requirement*: FR-023 specifies that the generator must run standalone via a self-contained default configuration when `custom_config.py` is missing.
2. **FR-029 Legend Occlusion Threshold & Culling Deviation**:
   - `generator.py:1397` sets default `occlusion_threshold=0.70` (spec FR-029 / SC-016 and T042 specify $\ge 0.85$).
   - More critically, `cull_occluded=True` defaults to active at the call site, dropping occluded marks completely from the output rather than retaining them with `visibility: 0` (amodal retention principle specified in FR-011/FR-012/FR-029).
3. **FR-022 / FR-030 Viewport Clipping Simplification**:
   - `clip_polygon_to_viewport` (`generator.py:1941-1944`) and `stroke_to_polygon_ribbon` (`generator.py:2060-2064`) use per-vertex clamping (`np.clip`) rather than an analytic Sutherland–Hodgman polygon-rectangle intersection. While functional for mild boundary overflows, complex concave polygons exiting and re-entering the viewport can produce degenerate or self-intersecting edges.
4. **FR-006 Baseline-Linkage Distance Hardening Untouched**:
   - In `generator.py:2667-2677` (`add_graph_topology_metadata`), bar matching relies purely on X-containment and nearest Y-distance with no maximum plausibility threshold. Bars distorted by exaggerated margins or twinx configurations can still link to implausibly distant baselines.
5. **Architectural Modularization Deferred per Ponytail Rules**:
   - The original `plan.md` called for decomposing `generator.py` into `geometry/transforms.py`, `geometry/obb.py`, `annotate/label_visibility.py`, and `annotate/series_link.py`.
   - *Context*: Under Ponytail guidelines enforced during Phase 1, speculative package scaffolding was deliberately pruned to keep changes surgical within `generator.py`. While functionally validated and fully tested, architectural modularization remains deferred until the major Phase 9/10 vector backend migration.
6. **Memory Hygiene Framing**:
   - Adding `try/finally: plt.close(fig)` inside `generate_single_chart` (`generator.py:4328`) is good local hygiene, but the outer `generate_single_chart_task` already contained `finally: plt.close('all')` prior to this modernization. The risk of worker memory leaks was already mitigated.
